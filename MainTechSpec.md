# Единое ТЗ: Falcon Tech Vehicle ReID

Рабочая спецификация для разработки, обучения, проверки и сдачи решения. Версия 2.0, 17.09.2026.

Здесь зафиксированы требования и ограничения задачи. Архитектуру модели и способы реализации команда выбирает самостоятельно. Рекомендации по разработке обозначены отдельно. Неуточнённые детали собраны в [открытых вопросах](Аудит_Единого_ТЗ_Falcon_Tech_Vehicle_ReID.md); они не блокируют начало разработки, но требуют сверки перед окончательной сдачей.

## 1. Цель и границы задачи

Разработать **open-set Vehicle Re-Identification**: находить один и тот же автомобиль на изображениях с разных камер по внешнему виду, без использования государственного номера.

На вход подаются полный статичный кадр JPEG/PNG и BBox целевого автомобиля. Решение вырезает автомобиль, формирует эмбеддинг, ищет совпадения в статической gallery и выдаёт:

- ранжированный top-10 для каждого query;
- отдельно — принятых кандидатов с уверенностью либо отказ, если уверенного совпадения нет.

Автомобили в train и test не пересекаются по идентичности. Модель должна обобщаться на ранее не встречавшиеся автомобили, а не только классифицировать обучающие ID.

Детекция, трекинг, обработка видео и выбор кадра из потока не входят в задачу. BBox уже предоставлен. Веб-интерфейс, API, микросервисы и внешняя БД для основной оценки не требуются: достаточно воспроизводимого batch-pipeline.

## 2. Данные

### 2.1. Структура и аннотации

```text
dataset/
├── images/              # плоский каталог JPEG, <image_id>.jpg
├── train.csv
├── test_query.csv
└── test_gallery.csv
```

| Файл | Столбцы в порядке следования | Строк в открытом наборе |
|---|---|---:|
| `train.csv` | `image_id,x,y,w,h,vehicle_id,camera_id` | 9 556 |
| `test_query.csv` | `image_id,x,y,w,h` | 1 110 |
| `test_gallery.csv` | `image_id,x,y,w,h` | 750 |

Всего в открытом наборе 11 416 изображений. Один кадр соответствует одному `image_id` и одному размеченному автомобилю. `image_id` уникален внутри каждого CSV; отдельного `object_id` нет.

- `x`, `y` — левый верхний угол BBox; `w`, `h` — ширина и высота в пикселях исходного кадра. Минимальный порог размера BBox не задан.
- `vehicle_id` — целочисленный идентификатор автомобиля.
- `camera_id` — анонимный идентификатор камеры без времени и геопривязки.
- В тесте `vehicle_id` и `camera_id` скрыты и доступны только организаторам для оценки.

`camera_id` разрешён для PK-sampling, cross-camera валидации и локального воспроизведения junk-фильтра. **Передавать его или производные от него признаки модели нельзя.** На инференсе эти данные недоступны.

Закрытый тест использует ту же структуру CSV и формат имён изображений. Размеры массивов и число выходных строк вычисляются по входным файлам, без привязки к числам открытого набора.

### 2.2. Состав теста и условия съёмки

В открытой тестовой части у каждого query есть пара в gallery. В закрытой части около **20% query не имеют соответствующего автомобиля в gallery** и никак не помечены. Для остальных гарантирован хотя бы один позитив с другой камеры.

Данные включают разные ракурсы, освещение, погоду, перекрытия и низкое качество изображения. Тестовые автомобили сняты минимум с двух точек наблюдения; это не означает наличия пары в gallery для каждого query.

### 2.3. Номерные знаки и лица

Номера и лица уже размыты. Координаты или маски номеров не предоставляются; дополнительное выделение номерной зоны не требуется.

**Запрещено использовать остаточные признаки номера**, включая характерные артефакты размытия, как идентифицирующий сигнал. Для финалистов предусмотрен контрольный прогон с номерной зоной, закрытой сплошной заливкой. Заметное падение качества разбирается на защите.

Предобучение на открытых внешних датасетах с читаемыми номерами разрешено без обязательного маскирования, но итоговое решение должно соблюдать запрет использования номерного сигнала конкурсных данных.

## 3. Pipeline и независимость запросов

Одной командой решение принимает `images/`, CSV query и gallery, выполняет базовую валидацию входа, декодирование, crop по BBox, preprocessing, извлечение эмбеддингов, поиск и формирование трёх файлов сдачи. Postprocessing, нормализация и re-ranking применяются в соответствии с выбранной реализацией.

Размерность эмбеддинга `D`, backbone, обучение, losses, similarity и вспомогательные модели выбирает команда. Допускаются cosine similarity и L2 по нормированным векторам. Индекс статической gallery можно построить заранее.

**Каждый query обрабатывается независимо**, даже при пакетном запуске. Для его результата доступны только сам query и вся статическая gallery. Нельзя использовать другие test-query, их эмбеддинги, статистику или результаты обработки для улучшения текущего ответа. Это проверяется по коду.

Разрешены TTA одного изображения, k-reciprocal и другой re-ranking внутри top-K gallery-кандидатов одного query, включая pairwise/local-feature модели. Финальный ranking может отличаться от простого cosine-поиска, но должен воспроизводиться кодом; применённая логика описывается в README решения.

Запрещены query expansion, кластеризация всех test-query, любые методы обмена информацией между test-query, использование истинных ID закрытого теста, дообучение и подбор параметров по закрытым ответам. Отдельного разрешения на варианты query expansion только по gallery нет; они не считаются разрешёнными автоматически.

## 4. Три обязательных файла результата

### 4.1. `submission.csv` — ранжирование

```text
query_id,gallery_id_1,gallery_id_2,...,gallery_id_10
```

Одна строка на каждый query, **ровно 10 gallery-кандидатов** по убыванию итоговой близости. `query_id` и `gallery_id_k` — соответствующие `image_id` входных CSV.

Файл включает все query, даже open-set и отклонённые моделью. Отказ здесь не кодируется: пустые строки, пропущенные query и специальные значения не допускаются. Дополнительный столбец score не нужен. По этому файлу считается основная метрика mAP@10.

### 4.2. `embeddings.npy` — представления модели

Матрица формы `(N_query + N_gallery, D)`, порядок строк:

1. все query в порядке `test_query.csv`;
2. все gallery в порядке `test_gallery.csv`.

Дополнительной сортировки нет. Для открытого набора форма — `(1860, D)`. Отдельный файл ID не нужен: соответствие задаётся порядком строк.

Рекомендуемый dtype — `float32`; другие типы организаторы приводят к нему. L2-нормализация перед сохранением необязательна: перед cosine-сравнением векторы нормализуются на стороне оценки.

Для каждого объекта обязателен фактический эмбеддинг модели, даже при малоинформативном кропе. Специального кода «неинформативности» нет.

Файл нужен для проверки происхождения результата и справочных embedding-метрик. Он не обязывает итоговый `submission.csv` совпадать с cosine-ranking, если используется воспроизводимый re-ranking.

### 4.3. `candidates.csv` — ответ или отказ

Обязательный заголовок и порядок столбцов:

```text
query_id,gallery_id,confidence
```

`confidence` — числовая оценка, больше означает увереннее. Диапазон `[0,1]` и калиброванная вероятность не требуются. На query разрешено любое число кандидатов; F1/TNR учитывают только кандидата с максимальным confidence.

**Отказ — полное отсутствие строк query в этом файле.** Не следует кодировать его пустым ID или специальным значением.

Команда сама применяет выбранный порог, указывает и обосновывает его в README. Организаторы не выполняют дополнительного отсечения по confidence: ответ уже выражен наличием строки. `submission.csv` в расчёте F1/TNR не участвует.

## 5. Оценка поиска

### 5.1. Позитивы, негативы и junk

Для query и объекта gallery:

| Условие | Роль в retrieval-оценке |
|---|---|
| Тот же `vehicle_id`, другая камера | Валидный позитив |
| Тот же `vehicle_id` и та же камера | Junk, исключается из ranking |
| Другой `vehicle_id`, в том числе с той же камеры | Валидный негатив |

Query без валидного позитива во всей gallery исключается из mAP и Rank, а не получает AP=0. Такой query оценивается в режиме отказа.

Junk удаляется до отсчёта оцениваемых позиций. **Не уточнено, как восполняется десятка после удаления junk из файла, содержащего только 10 кандидатов.** Формат сдачи остаётся прежним; точное поведение нужно сверить с официальным evaluator. Нельзя самостоятельно дополнять ranking из эмбеддингов и считать это подтверждённым протоколом. На тесте участник не может выполнить официальный junk-фильтр: нужные метки скрыты.

### 5.2. Основная метрика mAP@10

Для query с `n_pos(q) > 0` обозначим:

- `n_pos(q)` — число валидных позитивов во всей gallery;
- `rel_k` — 1, если кандидат на позиции `k` после junk-фильтрации является позитивом, иначе 0;
- `L_q ≤ 10` — длина оцениваемого списка после фильтрации и ограничения top-10.

```math
P@k = \frac{\sum_{i=1}^{k} rel_i}{k},
\qquad
AP@10(q) = \frac{\sum_{k=1}^{L_q} P@k\,rel_k}{\min(n_{pos}(q),10)}.
```

```math
mAP@10 = \frac{1}{|Q^+|}\sum_{q\in Q^+} AP@10(q),
\qquad Q^+ = \{q:n_{pos}(q)>0\}.
```

Усреднение — **macro по query**. Формула не разрешает вопрос формирования `L_q` при удалении junk из переданной десятки; он остаётся открытым. Основной балл качества считается по `submission.csv`, включая разрешённый re-ranking.

### 5.3. Дополнительные метрики

Rank-1 и Rank-5 показывают наличие валидного позитива в первых 1 и 5 позициях. Query без позитивов исключаются. Точный источник ranking для этих двух метрик ещё нужно сверить с evaluator.

Полный mAP и mINP рассчитываются из `embeddings.npy` справочно. Для mINP используется полное cosine-ranking L2-нормированных векторов с тем же junk-фильтром; равные score упорядочиваются стабильно по порядку `test_gallery.csv`.

```math
INP(q) = \frac{n_{pos}(q)}{rank_{last}(q)}.
```

`rank_last` — позиция последнего валидного позитива после удаления junk. mINP — macro-среднее по query с позитивами. Полный mAP, mINP и PR-AUC в баллы не входят; Rank-1/5 публикуются отдельными дополнительными метриками.

## 6. Оценка ответа и отказа

Оценка выполняется на уровне query, не отдельных пар и не identity. Используется верхний по confidence принятый кандидат. Под наличием пары понимается наличие валидного cross-camera позитива в gallery.

| Событие | Условие |
|---|---|
| TP | Пара есть, ответ возвращён, верхний кандидат верен |
| FP | Ответ возвращён, но верхний кандидат неверен или пары в gallery нет |
| FN | Пара есть, но решение отказалось |
| TN | Пары нет, решение отказалось |

Неверный ответ при существующей паре учитывается как FP; дополнительный FN за этот же query не предписан. Метрики считаются **micro**: один раз по суммарным счётчикам всей выборки.

```math
F1 = \frac{2TP}{2TP+FP+FN},
\qquad
TNR = \frac{TN}{TN+FP_{open}}.
```

`FP_open` — только ответы на query без валидной пары. В знаменатель TNR нельзя подставлять все FP. Правила обработки junk среди кандидатов и равных максимальных confidence требуют сверки с evaluator.

```math
CandidateScore = 0.10\,(0.7\,F1 + 0.3\,TNR).
```

PR-AUC считается справочно по `candidates.csv` на уровне query: label=1 при наличии валидной пары, label=0 при её отсутствии. Это метка наличия пары, а не правильности выбранного кандидата. Способ назначения score отсутствующим в файле query и точный расчёт кривой пока не уточнены.

## 7. Производительность и ресурсы

### 7.1. Стенд и измерения

| Параметр | Значение |
|---|---|
| GPU | NVIDIA RTX A5000, Ampere SM86, 24 ГБ VRAM |
| CUDA | Объявлено «CUDA драйвер: 12.2» |
| CPU | 2 × Intel Xeon Gold 6338, 2.00 ГГц |
| Ядра / потоки | 32 / 64 на сокет, всего 128 логических CPU |
| GPU в Docker | `--gpus all` |

Замеры выполняются на GPU. FP16/BF16, ONNX Runtime, TensorRT и TorchScript разрешены. Объём RAM, доступный диск и точные версии Toolkit/runtime пока неизвестны. Инференс не должен приводить к OOM.

Измеряемый extraction-цикл: **чтение с диска → декодирование → crop → preprocessing → forward → postprocessing → L2-нормализация**, то есть работа внутри `extract()`. Поиск по gallery и re-ranking в этот бенчмарк не входят и могут измеряться отдельно справочно.

- **Latency:** медиана полного цикла, batch=1; 50 прогревочных и 300 измеряемых прогонов; CUDA-синхронизация до и после каждого замера.
- **Throughput:** устойчивый FPS без очередей и деградации памяти; batch sizes 1, 8, 16, 32; не менее 10 секунд на каждый размер; в балл идёт лучший FPS.
- Дополнительно фиксируются пиковая VRAM, время загрузки весов, суммарный размер весов и детерминизм двух прогонов.

Для `t` в миллисекундах и лучшего `f` в FPS:

```math
latency\_score = \max(0,\min(1,(80-t)/40)),
\qquad
throughput\_score = \max(0,\min(1,(f-50)/50)).
```

Полный балл latency при `t ≤ 40 мс`, нулевой при `t ≥ 80 мс`; полный throughput при `f ≥ 100`, нулевой при `f ≤ 50`; между границами — линейно.

```math
PerformanceScore = 0.10\,latency\_score + 0.10\,throughput\_score.
```

### 7.2. Весовые файлы и полный запуск

**Не более 2 ГБ суммарно на все веса инференса**, включая backbone, auxiliary-модели, классификаторы атрибутов, ансамбли и reranker. Замер учитывает файлы в каталоге решения с расширениями:

```text
.pt .pth .bin .onnx .engine .plan .safetensors .ckpt .trt .pb .tflite .npz
```

Превышение лимита означает недопуск к оценке производительности, а не постепенный штраф.

Ориентир времени полного прогона — `latency_batch1 × n_test × 3`, около 4 минут для объявленного объёма закрытого теста. Это не подтверждённый фиксированный тайм-аут; определение `n_test` и границы полного таймера ещё нужно уточнить. Исключение поиска из extraction-бенчмарка не означает его исключения из времени полного запуска.

## 8. Обучение, внешние ресурсы и локальная проверка

Разрешены публичные предобученные веса и внешние датасеты, включая DINOv2/DINOv3, исследовательские/некоммерческие лицензии и gated-access по заявке. Организаторы должны иметь возможность самостоятельно открыть и проверить источник. Правило распространяется и на вспомогательные модели подготовки данных, масок и разметки.

Непроверяемые приватные репозитории, внутренние датасеты и модели без публичной ссылки недопустимы. Все внешние ресурсы перечисляются в README с URL, автором и версией/тегом. Публичные предобученные веса фиксируются также контрольной суммой.

**Рекомендуемая локальная валидация:** выделить независимую часть train по identity, использовать camera ID для cross-camera оценки и включить ID, полностью отсутствующие в локальной gallery. Ориентир — около 20% отложенных ID без пары; доля ID и доля query могут различаться при разном числе снимков. Порог отказа можно калибровать на этом split. Анализ ошибок на такой размеченной части train разрешён и рекомендуется.

Для первого рабочего решения достаточно encoder, поиска по gallery и порога отказа. Re-ranking, ансамбли и веб-демо — последующие варианты развития, а не условия начала работы. Это рекомендация порядка разработки; выбор модели и алгоритмов остаётся за командой.

## 9. Запуск и воспроизводимость

Обязательный результат — pipeline, который одной командой в Docker обрабатывает каталог изображений и оба тестовых CSV и сохраняет три файла результата. API-вызов по одному query не требуется.

- При `docker build` интернет разрешён, при запуске контейнера и инференсе — полностью запрещён. Всё необходимое к запуску уже находится в образе.
- Версии пакетов фиксируются точно. Веса хранятся в репозитории либо скачиваются в Dockerfile по фиксированному URL с проверкой checksum; меняющиеся ссылки на latest не подходят.
- Инференс должен соответствовать контракту `extractor.py`. Допускается Python или другой язык, совместимый с контрактом. Сам контракт ещё нужно получить.
- Предпочтительны свободное ПО либо ПО из отечественного реестра, работающее под Linux; конкретный стек не навязывается.

В репозитории обязательны код обучения и инференса, `Dockerfile`, `docker-compose.yml`, файл зависимостей, необходимые для воспроизведения конфигурации и README. Исходники открытые, не обфусцированные, с понятными комментариями и в соответствии с документацией. По запросу жюри нужно быть готовыми показать сборку и исполнение.

Невоспроизводимые решения, использование номерных признаков и непроверяемых внешних данных приводят к недопуску. Результаты должны быть получены моделью и воспроизводиться pipeline; ручное составление submission не соответствует задаче.

## 10. Итоговая оценка

| Критерий | Вес | Основа |
|---|---:|---|
| Точность | 45% | mAP@10 на закрытом тесте по `submission.csv` |
| Производительность | 20% | По 10% за latency и throughput |
| Инженерное качество | 15% | Воспроизводимость, код, контейнеризация, документация |
| Режим кандидатов | 10% | `0.7 × F1 + 0.3 × TNR` |
| Защита | 10% | Обоснование методологии, архитектуры, порога и анализ ошибок |

Все метрики в формулах баллов используются в диапазоне `[0,1]`; `CandidateScore` и `PerformanceScore` — доли общего балла. Веса суммируются до 100%.

Автоматического лидерборда во время хакатона нет. После завершения организаторы запускают решения на закрытом тесте и измеряют метрики и скорость своими скриптами. Собственные замеры команды справочные и не дают баллы за производительность.

## 11. Документация и сдача

README должен описывать функциональную и компонентную архитектуру, обработку данных и алгоритмы, применённый re-ranking, сборку/установку/запуск одной командой, validation-метрики, порог отказа и его обоснование, внешние библиотеки, модели и датасеты с версиями. При необходимости можно приложить расширенный PDF.

Презентация в PDF/PPTX ориентируется на техническую и бизнес-аудиторию. В ней нужны методология и архитектура с обоснованием backbone и устойчивости к ракурсу/освещению, схема пользовательского пути, план масштабирования и честный анализ ошибок с примерами. Порог отказа обосновывается на защите.

Для сдачи предусмотрены ссылки на Git-репозиторий, презентацию, работающий прототип и отдельную документацию `.doc`/`.pdf`, если она вынесена из README. Как оформить ссылку на прототип для batch-only решения, пока не разъяснено; обязательного веб-сервиса из этого не следует.

## 12. Дополнительные возможности

При равенстве основных результатов могут учитываться веб-демо, интерпретируемость модели (Grad-CAM/attention maps), ANN-поиск по gallery порядка `10^6` объектов и подробный разбор ошибок. Эти возможности не добавляют баллов сверх 100%.

Если делается веб-демо, оно принимает изображение и BBox, наглядно показывает кандидатов, confidence и отказ, позволяет экспортировать результаты. Самостоятельная детекция автомобиля не требуется. Стек интерфейса и API свободный, формальной проверки API нет. Полный представляемый сервис также запускается одной командой и работает офлайн.
