# Что известно о данных и оценке

Большая часть чисел воспроизводится командой `DATA_ROOT=./dataset python3 scripts/analysis/data_structure.py`. Исключения: замеры декодирования (раздел 3) и оценка по фону (раздел 2.2) сделаны разовыми проверками, их источник указан рядом. Анализ от 18.09.2026.

## 1. Данные

- **train:** 9 556 кадров, 1 541 `vehicle_id`, 96 `camera_id`.
  - На машину 4–8 кадров, в среднем 6,2.
  - На машину 2–8 камер, в среднем 2,5; у 1 028 машин ровно 2 камеры.
- **Кадров на пару (машина, камера):** по 1 кадру — 551 группа, по 2 — 994, по 3 — 2 339. Это серии кадров одной съёмки.
- **Кадры:** все 1920×1080 JPEG, около 650 КБ, всего около 7 ГБ.
- **BBox крупные:** медиана около 670×485 px, 5-й процентиль около 400×340. Разрешение для входа 224–320 px не проблема.
- **Изображения train, query и gallery не пересекаются.**
- **Съёмка уличная, с разных ракурсов** (перед, зад, бок). Много перекрытий соседними машинами, в BBox часто попадает чужая машина. Есть спецтехника, например экскаватор-погрузчик JCB.

## 2. Устройство открытого теста: у каждого query есть «брат» с той же камеры

### 2.1. Гипотеза и проверка

**Гипотеза:** gallery содержит ровно один кадр на каждую пару (машина, камера), а в query попали все остальные кадры.

Проверка на четырёх независимых числах: предсказание по train, пересчитанное на размер теста, против факта.

| Величина | Предсказание | Факт |
|---|---:|---:|
| Размер gallery | 756 | 750 |
| Размер query | 1 104 | 1 110 |
| Query, у которых в gallery есть кадр с почти тем же BBox (±10 px) | 592 | 583 |
| Пар query–query с почти тем же BBox | 243 | 248 |

Дополнительные подтверждения:
- у каждого query не больше одного такого кадра в gallery;
- внутри gallery таких пар 0;
- в контрольной проверке с перемешанными координатами совпадений 0.

### 2.2. Следствия

- **У каждого парного query в gallery ровно один junk-брат** — кадр той же машины с той же камеры, почти всегда из той же серии. Эмбеддинг-модель почти наверняка поставит его на первое место.
  - **mAP@10.** Junk удаляется до обрезки до 10 позиций, добора нет. Брат в top-10 просто съедает один слот; штрафа за него нет.
  - **`candidates.csv`.** Двойник засчитывается как верный ответ (D-023), поэтому его надо оставлять первым кандидатом. На zero-shot модели это даёт 0,7·F1 + 0,3·TNR = 0,855.
  - **Фильтр двойников не нужен.** Идеальный фильтр в `submission.csv` даёт +0,0007 mAP@10, то есть +0,03 балла из 45 (D-024).
- **Двойник никогда не бывает валидным позитивом.** На train все 4 275 пар одной машины с почти тем же BBox сняты одной камерой; между разными камерами таких пар 0. Ещё 193 пары с почти тем же BBox относятся к разным машинам — это негативы. Значит, понижать двойников в выдаче безопасно при любом поведении evaluator.
- **По BBox находится только около 53% братьев.** Столько same-camera пар одной машины на train имеют почти тот же BBox (0,534). Остальных ловим по сцене, то есть по фону кадра за пределами BBox. Проверка на подвыборке train из 120 машин: разница уменьшенных до 32×18 кадров с замаскированной машиной при пороге 0,12 находит 58% пар с одной камеры при 0,07% ложных срабатываний, при пороге 0,15 — 77% при 2%. Обученный дескриптор сцены даст больше.
- **Позитивов на query мало.** `n_pos` = число камер машины − 1, и у двух третей машин это ровно 1. Поэтому mAP@10 фактически определяется рангом одного позитива, и Rank-1 решает почти всё.
- **Закрытый тест.** Там около 20% query без пары. Если такие машины просто убраны из gallery, то у этих query нет и брата. Тогда наличие брата означает, что машина есть в gallery. Использовать это как признак confidence — серая зона, по умолчанию выключено (DECISIONS D-008).

## 3. Скорость: узкое место — декодирование JPEG

- В замер задержки входит чтение и декодирование полного кадра 1920×1080.
- PIL на MacBook тратит на декодирование и crop 38,7 мс на кадр. С `draft` (DCT-масштаб 1/2) — 19,9 мс. Полный балл дают при ≤ 40 мс на **весь** цикл.
- Процессор стенда — Xeon Gold 6338 на 2,0 ГГц. По одному потоку он, вероятно, медленнее.
- **Вывод:** декодировать на GPU (nvJPEG или DALI с декодированием только области BBox) либо с DCT-масштабированием под размер BBox. Сама модель ViT-B в FP16 по нашей оценке занимает единицы миллисекунд; это пока не измерено.

## 4. Ответы организаторов (Q&A)

- **Junk:** «Из ранжирования для запроса q удаляются объекты галереи, у которых одновременно тот же vehicle_id и тот же camera_id, что у q… Фильтр применяется до усечения до 10 позиций… он не занимает слот в топ-10 и не штрафуется — просто выбрасывается».
- **Query без позитивов** исключаются из mAP и Rank и оцениваются только в режиме отказа.
- **AP** нормируется на `min(n_pos, 10)`, усреднение по query (macro).
- **Стенд:** RTX A5000 24 ГБ (SM86), драйвер CUDA 12.2, 2× Xeon Gold 6338, 128 логических CPU, GPU внутри Docker через `--gpus all`. Замеры на GPU.
- **`camera_id`:** можно для PK-sampling и кросс-камерной валидации; подавать в модель нельзя.
- **`evaluate.py`** лежит на диске организаторов рядом с архивом датасета, в репозитории его ещё нет (задача H0.1).
- **Лицензии внешних ресурсов:** «Допустимы любые публично доступные веса и датасеты, для которых можно однозначно указать источник (URL, версия/тег релиза, автор), — независимо от типа лицензии (включая CC BY-NC, gated-access по заявке, DINOv2/v3…)». Требование распространяется и на вспомогательные модели: детекцию, маски, разметку. Недопустимы только источники, которые организаторы не могут открыть сами.
- **Кандидаты:** «Метрики (F1, TNR) считаются только по верхнему кандидату — тому, у которого максимальный confidence для данного query_id… Остальные кандидаты ниже верхнего в расчёт не входят никак». Число кандидатов не ограничено, confidence может быть в любой шкале, важен только порядок. Отказ — отсутствие строк; пустые `gallery_id` скрипт игнорирует.
- **Query, у которых единственный позитив — junk,** исключаются из mAP. Правильный ответ для них в `candidates.csv` — отказ.
- **Re-ranking:** в `submission.csv` можно применять «любую другую логику переранжирования, не использующую другие query», включая pairwise- и local-feature-модели поверх top-K. Понижение двойников под это подпадает (D-014).
- **Закрытый тест** «собран тем же пайплайном… тот же протокол сплитов», и в нём около 20% query без пары. Значит, двойники будут и там, а наша схема фолдов верна.
- **Лимит на весь прогон:** ориентировочно `latency_batch1 × n_test × 3`, около 4 минут для закрытого теста. Независимость query проверяют по коду.
- **Кандидаты (из кода `evaluate.py`, 20.09):** junk из кандидатов не удаляется, верхний по confidence считается верным при совпадении `vehicle_id`. Двойник с той же камеры — **верный ответ** (D-023). Равные confidence разрешаются порядком строк в файле.
- **`submission.csv` читается без заголовка** (D-025).
- **Не решено:** контракт `extractor.py`; доступные RAM и диск стенда.

## 5. Как выгоднее считать режим кандидатов

- F1 = 2TP / (2TP + FP + FN). Отказ на query, **у которого пара есть**, но top-1 неверный, превращает FP в FN, и F1 от этого не меняется.
- Поэтому порог должен ловить именно query **без пары** (FP → TN улучшает и F1, и TNR) и при этом не отказывать там, где top-1 верный.
- «Неуверенные» ответы на query с парой отсекать бесполезно.

## 6. Zero-shot DINOv2: модель сравнивает сцену, а не машину

Эксперименты A-001 и A-002, DINOv2 ViT-B/14 без дообучения, вход 224, 5 фолдов:
- **mAP@10 около 0,07, Rank-1 около 0,06–0,07.** Случайный уровень — около 0,01.
- **Junk-брат стоит на первом месте у 86,8% query** (fold 0). Наивная политика «всегда отвечать top-1» даёт F1 около 0,01: почти все верхние ответы — двойники.
- **Среди top-10 без junk 20% — другие машины с той же камеры, что query.** Во всей gallery их 3%, перекос почти в 7 раз. Без дообучения модель сравнивает фон и сцену, а не саму машину.

Выводы:
- дообучение обязательно, и при обучении нужно гасить влияние фона: тесный кроп, аугментации фона, PK-sampler с разными камерами;
- zero-shot DINOv2 — хороший детектор «той же сцены». Это пригодится треку B для двойников, если позволит бюджет скорости.
