# Архитектура D082

Решение разделяет три задачи: найти похожие автомобили, определить порядок
близких кандидатов и решить, достаточно ли оснований для совпадения.
Их оценки используются по-разному: итоговый ranking score не выдаётся за
вероятность и не подменяет confidence для отказа.

## Изображение → представление

Общий JPEG decode даёт RGB-кадр; по входному BBox вырезается автомобиль.
Каждый encoder получает свой размер: DINOv2-B/14 — 392×392,
CLIP-B/16 — 288×288. Общая реализация crop/resize/normalize находится
в [preprocess.py](../reid/data/preprocess.py).

Модели возвращают pre-BN features. Компоненты нормализуются отдельно,
масштабируются фиксированными коэффициентами из артефакта и объединяются
в L2-нормированный вектор размерности 3072. Эти коэффициенты не оцениваются
по текущим query. Исторические NumPy-нормализации сохранены для точного
совпадения replay, production и ускоренного извлечения.

## Gallery → кандидаты → порядок

[GalleryPolicy](../reid/post/gallery_policy.py) предварительно вычисляет
сходства gallery–gallery. Hub correction уменьшает преимущество объектов,
которые похожи сразу на множество других автомобилей.

[PreparedRankerGallery](../reid/post/ranker.py) сохраняет исходные эмбеддинги
двух компонент. Внутри top-10 для каждого query отдельно строятся:

- 13 признаков узла: сходства и ранги двух encoder, локальные z-оценки,
  gallery hub-признаки и отступы от максимального сходства;
- два канала рёбер: сходства gallery–gallery в каждой компоненте.

Компактная графовая модель предсказывает residual для порядка кандидатов.
Парный DINOv2-S/14 verifier обрабатывает исходные изображения query и десяти
кандидатов в том же окне. Итог объединяет стандартизированные исходные
оценки, verifier с весом 0,15 и graph residual с весом 0,5. Набор top-10
сохраняется, меняется порядок. Модель графа: [list_ranker.py](../reid/model/list_ranker.py);
загрузка проверенного all-data graph: [d082_production.py](../reid/infer/d082_production.py).

## Решение о совпадении

Confidence выбранного кандидата — его raw cosine, стандартизированный
по внедиагональным gallery–gallery сходствам. Это другая шкала, чем ranking.
Порог 6,6 зафиксирован вместе с рецептом. При отказе query отсутствует
в `candidates.csv`; для принятого query сохраняются три упорядоченных кандидата.

Оценка каждого query зависит только от него и статической gallery. Mean/std
для строки одного query относятся к его gallery-кандидатам, а не к другим
query. На инференсе нет camera ID, query expansion или адаптации модели.

## Ускорение с сохранением результата

[D082Extractor](../reid/infer/d082_extractor.py) используется штатным
[run.py](../reid/infer/run.py) и [скоростной проверкой](../scripts/bench_final_candidate.py).

- Очередь предобработки ограничена восемью элементами и сохраняет порядок.
  CPU подготавливает следующую четвёрку во время CUDA forward текущей.
- Для каждого encoder CUDA Graph владеет входным contiguous fixed4 буфером.
  Replay сокращает накладные расходы запуска без изменения FP16-вычислений.
- Singleton декодируется и передаётся один раз. На GPU он broadcast-копируется
  в ту же четвёрку; экономия H2D — 8517888 байт на запрос.
- Отложенные проверки и возврат компонент выполняются для внешнего вызова;
  NaN/Inf/zero по-прежнему вызывают ошибку до публикации результата.
- Lock сериализует доступ к graph-буферам. Возвращённые CPU-массивы принадлежат
  вызвавшему коду и не перезаписываются следующим replay. При ошибке очередь
  дренируется перед следующим вызовом.

Нет ожидания поступления дополнительных query. Для CPU предусмотрен
reference fixed4 путь с той же нормализацией. Precision, разрешения,
веса, порог, verifier и graph не меняются при ускорении.

## Границы

Предрасчёт gallery–gallery требует O(N_gallery²) памяти; production использует
точный поиск. Синтетическая ANN-демонстрация из исторической презентации
не является проверенной заменой этого поиска.

Extraction FPS не равен пропускной способности полного сервиса с verifier.
Проверенный plate-control ограничен объёмом и полнотой аннотаций. Финальные
all-data веса не дают независимой OOF-оценки на тех же данных. Все числа
и ограничения собраны в [протоколе](d082_acceptance.md).
