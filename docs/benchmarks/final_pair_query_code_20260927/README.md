## Два разных утверждения, которые нельзя смешивать

1. **Независимость от содержимого других query:** при фиксированных модели, gallery,
   своём изображении/BBox и форме операции замена остальных query не должна менять
   собственные embedding, ranking, confidence или отказ. Аудит кода поддерживает
   это утверждение; прямой GPU-контроль финальной пары ещё нужен.
2. **Точная численная эквивалентность разных форм операции:** FP16 forward при
   batch=1 и batch=32 может выбрать разные вычислительные kernels/порядок редукций.
   Сам confidence-only drift не доказывает передачу информации между query, но
   и не даёт права обещать побитовую эквивалентность. Вблизи порога или равных
   ranking scores такой drift потенциально способен менять дискретное решение.

Старый результат тройки остаётся опубликованным strict FAIL:
на 24 train-query top-10, ID кандидатов и решения об отказе совпали, но singleton
против batch дал confidence drift до 0.001421. Это **не замер финальной пары**.
`scripts/check_query_independence.py:113–133` сравнивает все варианты с batch=1,
поэтому его общий `passed` смешивает оба утверждения. Ослаблять tolerance,
округлять confidence или менять этот FAIL задним числом не требуется.

## Рекомендуемый следующий контроль на GPU

Все входы — заранее зафиксированные train-кадры, без выбора по тестовым результатам.

- Извлечь статическую gallery один раз фиксированным способом и использовать её
  неизменной во всех сравнениях.
- Для набора фиксированных anchor-query выполнить batch ровно 32: один anchor на
  фиксированной позиции плюс 31 train-сосед. Повторить с **полной заменой всех 31
  соседей**, сохранив anchor и форму операции. Сравнить его embedding побитово,
  затем точные top-10, candidate IDs/confidence и отказ. Проверить несколько
  фиксированных наборов соседей. Это не тюнинг параметров.
- Отдельно проверить перестановку при той же форме batch, выравнивая ответы по
  ID, и порядок вызовов, чтобы обнаружить скрытое изменяемое состояние.
- Сохранить без изменений существующий batch=1/32 строгий отчёт как численную
  диагностику. Для пары отдельно записать максимальный drift и число изменений
  top-10, candidate IDs и отказов. Не переносить цифры тройки на пару.
- Два полных запуска при одинаковой конфигурации должны по-прежнему давать
  побитово одинаковые три файла сдачи; это самостоятельный гейт детерминизма.

В итоговом отчёте полезны отдельные поля `content_isolation`,
`fixed_shape_exact_equivalence`, `cross_shape_strict_equivalence` и
`cross_shape_rank_candidate_acceptance_equal`, со scope и размером проверенного
набора. **Пока реальные измерения не выполнены, GPU-поля — NOT RUN.** Если итоговая
приёмка трактует query-independence как отсутствие информационной зависимости,
а не равенство каждого бита между разными kernels, это нужно явно закрепить в
решении и README, сохранив исходную строгую диагностику. Нельзя молча поменять
смысл ранее опубликованного `passed` или заявить доказательство для всех входов.
