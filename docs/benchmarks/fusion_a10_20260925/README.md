# Fusion: независимая техническая проверка B, 25–26.09.2026

Это **технический кандидат, не финальная приёмка B7.1/B7.2**. Тройка D-062:
DINOv2-B/14 392 cls_top16 + CLIP-B/16 288 cls_top16 + SigLIP2-B/16 288 top16,
склеенный эмбеддинг 3840. Все замеры здесь — **NVIDIA A10**, не A5000.

## Реальная скорость, а не экстраполяция

Один A10 24 GB, 8 vCPU, Ubuntu 26.04, драйвер 615.71.09; Docker CUDA 12.1,
Torch 2.5.1+cu121. Полный C5: чтение полного JPEG с диска, decode, BBox crop,
преобразование каждого участника, FP16 forward и L2. Decode общий для участников,
preprocess — 8 CPU workers. Fold0 query, 50 прогревов, 300 latency-измерений,
batch 1/8/16/32 по минимум 10 секунд. GPU-задачи выполнялись последовательно.

| Состав / веса | p50, ms | p90, ms | лучший FPS (batch32) | peak allocated, MiB | загрузка, s |
|---|---:|---:|---:|---:|---:|
| Тройка OOF, первый прогон | 54.936 | 76.829 | 78.54 | 1667.7 | 3.419 |
| Тройка OOF, повтор | **33.525** | 36.123 | **80.60** | 1667.7 | 3.541 |
| Тройка all-data | 33.420 | 36.026 | 78.88 | 1667.7 | 3.329 |
| DINO392 + CLIP288, OOF | **26.456** | 28.931 | **98.19** | 1313.0 | 2.198 |
| Тройка OOF, готовый self-contained образ | **32.254** | 35.113 | **80.77** | 1667.7 | 3.468 |

Первый прогон не удалён. Более медленный initial latency совместим с влиянием
I/O/дискового кэша; контролируемого эксперимента с очисткой кэша не было,
поэтому причина **не доказана**. Повторный OOF и all-data близки, но не равны.
Нельзя обещать «FPS ровно тот же» для разных запусков даже с одинаковым графом.

**На A10 тройка не достигает 100 FPS**, пара тоже немного ниже. Это сигнал риска,
не вердикт A5000: исторический коэффициент model-v1 не сертифицирует новую
тройку. Нужен прямой A5000 C5-замер именно выбранного состава. Пара здесь —
speed fallback; её качество и порог не приняты, состав автоматически не заменён.

В таблице только Extractor, **не поиск и не парный verifier**. VRAM — счётчик
Torch allocator, не весь процесс из nvidia-smi. Полный pipeline измеряется
отдельно при проверке детерминизма. `commit: null` в сырых JSON означает,
что `.git` не передавался на сервер/в образ; код bench/extractor взят из
`f3b88ca`, упаковка B — `d0e2180`, fusion smoke — `5c858c8`.

## Проверенные источники и сборка пакета

Все release assets получены с проверкой **размера и SHA-256** из GitHub API и
`SHA256SUMS.txt`. GitHub-токен не передавался на сервер или в образ. Во время
сетевых обрывов скачивание возобновлялось; неполные `.partial` не использовались.

- [OOF release](https://github.com/Timur713/hack_falcon_2026/releases/tag/fusion-oof-v0):
  `hires392_f0`, `div_clip_f0`, `div_siglip_f0`, `v_fus_f1only.pt` (input392).
  Сумма **1 160 606 944 bytes** = 1.081 GiB, меньше 2 000 000 000 bytes.
- [All-data release](https://github.com/Timur713/hack_falcon_2026/releases/tag/fusion-all-v1):
  три `*_all` и `v_fus_all_input168.pt`, сумма **1 159 624 032 bytes**.
  Метаданные all-data проходят, но автор сообщил о неудавшемся обучении verifier.
  Поэтому пакет подготовлен с **rerank_weight=0**, без заявления о качестве.
  Нулевой вес пропускает verifier forward; это не профиль рабочего input392 rerank.

`prepare_fusion_artifact.py` построил оба пакета по **полным train-кадрам и
fold0 gallery**, не test-query. Масштабы фиксируются в `fusion_config.json`.
OOF rerank_weight=0.15, all-data=0; порог 6.0 оставлен предварительным,
hub k=3/lambda=0.5. Тест использовался только для технического прогона/формата.

Манифест OOF: `00e9b5a91905e02f3cf93ca91cab737066e4cb4f24eae0534f273abcbccce5cd`.
Этот pin и fixed OOF URL стоят в opt-in Docker target `fusion`; legacy default
сохранён. Для другого пакета требуются явные SHA/URL. Полное описание:
[`docs/fusion_docker.md`](../../fusion_docker.md).

## Готовые контейнеры: реальные офлайн-проверки

Оба образа собраны и запущены **без сети и без bind mounts кода/моделей**:
`falcon-fusion:oof-v0` и `falcon-fusion:all-v1-technical`.
Веса/конфиги находятся внутри образа. Код упаковки/исправлений — `2a587dd`.

- По **271 pytest** внутри каждого образа, затем реальный smoke на 25 query
  и 25 gallery с fusion и verifier — PASS, без SKIP.
- Полные 1110 query + 750 gallery: все три C6-файла валидны;
  `embeddings.npy` имеет `(1860, 3840)`, float32.
- Два полных запуска каждого стека дали **побайтно идентичные все три файла**.
  SHA, размерность, image identity и время — в `offline_oof/`, `offline_all/`.
- OOF полный pipeline с input392 verifier: **140.83 / 130.14 s**, peak allocated
  **1791.4 MiB**, включая три embedder и verifier. Это не Extractor FPS из таблицы.
- All-data запускается с weight=0: verifier загружен, но forward пропускается.
  Его полный runtime нельзя использовать как скорость исправленного input392.
- OOF `--require-all-data` отвергнут по `components/0`, как и должен; all-data
  metadata принимает. Успешный metadata-гейт **не проверяет обученность/качество**.

Первый `docker build --network none` отказал на отсутствии apt-кэша. Штатная
сборка использовала сеть для зависимостей; установка весов выполнялась с
`RUN --network=none`, все запуски — с `docker run --network none`.
Сборка с нуля без сети **не заявляется**. Реальная контейнерная проверка также
обнаружила две ошибки (отсутствие `.dockerignore` в образе и обязательного `git`
у исследовательского отчёта); они исправлены, проверки повторены полностью.

## Полный train fold0: качество и заливка

Метрики получены **только** через `reid/eval/eval_local.py`, не по test:

| OOF fusion + рабочий `v_fus_f1only` | mAP@10 | official candidate score, threshold6 |
|---|---:|---:|
| Полные исходные кадры, FP16 | **0.871041340** | **0.959378499** |
| Та же цепочка с геометрической заливкой | **0.869207570** | **0.958161142** |

Candidate score выше следует **official** трактовке D-023: совпадение машины
на той же камере засчитывается. Отдельная строгая диагностика `cross_cam`
даёт score0.30967 / 0.31259; её нельзя выдавать за высокий cross-camera top-1.
Обе трактовки и все счётчики сохранены в JSON, алгоритм оценщика не менялся.

Падение mAP **0.001833769**. Маска: ширина 0.26 BBox, aspect4, центр (0.5,0.72),
fill127; применяется и к embedder, и к verifier. Покрытие реальных номеров
не проверено разметкой. Это стресс-контроль указанной области, **не доказательство
полной независимости от номера** и не эквивалент неизвестному контролю жюри.
All-data train-выходы для качества не оценивались: отложенного фолда у них нет.

Это один fold0 и один выбранный стек, не OOF5. Embedders декларируют обучение
`all except 0`, verifier — fold1; скрытый provenance mining/teacher не может
быть доказан этими метаданными. Число 0.87104 не переносится на all-data.
Порог не подбирался в этой сессии; финальную калибровку не считаем закрытой.

Повторное ранжирование **этих же full-frame embeddings** без verifier даёт
**0.858127289** против C4 replay 0.862851656: разница **−0.004724366**.
Нельзя заявить выполнение допуска cache→production ≤0.002 для нового стека.
Различаются cached JPEG, точность FP32/FP16 и масштабы; требуется отдельное
разложение факторов. Контроль старых C4-масштабов почти не меняет результат
(0.858180926), то есть **замена масштабов разрыв не объясняет**.
Подробности/команды — в соседнем replay-отчёте. Прирост verifier на одном
и том же новом входе составляет **+0.012914050**, не разность разных протоколов.

## Независимость от отчётных чисел A

Настоящий C4 replay fold0 уже выполнен отдельно:
[`fusion_replay_20260925`](../fusion_replay_20260925/README.md).
Fusion **0.844054509**, с hub **0.862851656**. Число A **0.863500007**
воспроизводится при доборе после удаления junk; C6 не позволяет такой добор.
Это малая, но реальная разница протокола. Окончательное качество полного
OOF image→verifier pipeline нужно отличать от CPU replay сохранённых дампов.

В новых A-099/A-100 есть полезный контроль 2×2 для заморозки backbone, но
обобщение «единственный фактор» ограничено проверенными рецептами и seed.
Новых checkpoint/logits эти коммиты не добавили. A-101 подтверждает неполное
совпадение окон; высокая доля пересечения **не доказывает** малое влияние на
mAP, поскольку различается ещё и z-нормировка verifier по 30 против 10.
Нельзя получить точный production replay простым переименованием старого числа.

## Воспроизведение

Изолированная серверная директория содержит `src`, `artifacts`, `outputs`, `logs`.
`DATA_ROOT` — существующий датасет, монтируемый read-only. Последовательно:

```bash
SESSION_ROOT=/path/to/session DATA_ROOT=/path/to/dataset bash scripts/fusion_a10_session.sh oof
SESSION_ROOT=/path/to/session DATA_ROOT=/path/to/dataset bash scripts/fusion_a10_session.sh all
SESSION_ROOT=/path/to/session DATA_ROOT=/path/to/dataset bash scripts/fusion_a10_compare.sh
# Подготовить src/artifacts/fusion_bundle из проверенного пакета без symlink.
SESSION_ROOT=/path/to/session DATA_ROOT=/path/to/dataset bash scripts/fusion_docker_session.sh oof
```

Выходные каталоги должны быть новыми. Эти скрипты **не выполняют Shelve**:
после копирования результатов отдельно освободить GPU через кабинет провайдера.

Все серверные `outputs/` и `logs/` сохранены на ноутбуке в игнорируемом
`artifacts/a10_session_20260925/results_20260926_0317.tar.gz` (196 MiB).
SHA-256 на сервере и после копирования совпал:
`ba01ba05a2f942fcef35e9e308e8fa9c3a094a6c045863e2a7a33984f4a06bb7`.
В Git включены компактные отчёты, конфиги, хеши, логи успешных сборок и команды,
а не веса или большие промежуточные embeddings. Канонический `submission/`
не заменялся непринимаемыми OOF/all-data-technical выходами.

A10 после backup переведена через Stop → Shelve в **SHELVED_OFFLOADED**,
подтверждение 26.09 03:22 МСК; GPU освобождён, том сохранён. Подробности
расходов/сбоя инструмента — `docs/infra.md`. Прямого теста A5000/R535 в этой
сессии не было. Итоговый локальный `make check`: **279 тестов**, C6 и legacy
real-image smoke50; дополнительно в каждом fusion-образе **271 тест** и
настоящий fusion/verifier smoke50. Восемь новых тестов CPU replay живут в docs
и не включаются в минимальный runtime image.
