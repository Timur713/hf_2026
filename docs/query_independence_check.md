# Проверка независимости query на финальном fusion

```bash
PYTHONPATH=. python scripts/check_query_independence.py \
  --model artifacts/models/fusion --verifier artifacts/models/fusion/verifier.pt \
  --data-root dataset --fold 0 --queries 24 --extras 8 \
  --device cuda --workers 8 --out outputs/query_independence
```

Скрипт берёт фиксированный prefix train-fold (20–32 query), сверяет IDs/BBox с
`train.csv`. Gallery извлекается один раз. Query извлекаются batch1, batch32,
в обратном порядке и вперемешку с другими query. Verifier включён; weight и
порог берутся из artifact, не переопределяются. Для каждого варианта сохраняются
входные CSV, три C6-файла и их проверка. Итог содержит SHA моделей/конфигов/входов
и скрипта. Test не используется; all-data веса допустимы, поскольку метрики
качества здесь не считаются и порог не подбирается.

`strict_byte_equivalence` относится к полям top10/candidates после выравнивания
по query ID, а не к переставленным строкам файлов или embeddings. Embedding
drift записывается без требования побитного равенства. Отдельно указаны совпадение
ранжированных ID, ID принятых кандидатов, решений ответ/отказ и максимальная
числовая разница confidence.

**Несовпадение только младших разрядов confidence не доказывает использование
других query.** FP16 kernels могут округлять по-разному при изменении формы
batch. Строгая проверка при этом возвращает `1`, сохраняя весь отчёт; это повод
разобрать численную стабильность, а не объявлять дисквалификацию. Даже изменение
ID около почти равных scores требует анализа причин, не автоматического вывода
об утечке. `0` — все строгие сравнения прошли, `2` — ошибка запуска/входов.

Выходной каталог не перезаписывается. PASS на ограниченной выборке не заменяет
проверку кода и не доказывает независимость на всех возможных входах.
